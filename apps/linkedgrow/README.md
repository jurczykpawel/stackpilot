# LinkedGrow - AI Agents for LinkedIn Lead Generation

Alternative to Expandi, Dripify and Lemlist. You describe who you sell to, and an agent looks for those people on LinkedIn, scores every profile it finds, sends the invitation, runs the first conversation and hands you the ones who want to talk. The posting side is the same product: a generator, an editor, a calendar and the analytics LinkedIn actually showed on your posts.

There is no LinkedIn API in this product. The worker drives a real Chrome signed in to your own account, which is why it needs more memory than a normal web app.

## Installation

```bash
./local/deploy.sh linkedgrow --ssh=ALIAS --domain-type=cloudflare --domain=linkedgrow.example.com
```

### Options

```bash
# Pin a published version instead of latest
LINKEDGROW_VERSION=sha-2701d11 ./local/deploy.sh linkedgrow --ssh=ALIAS --domain-type=cloudflare --domain=linkedgrow.example.com

# Force the number of concurrent Chrome sessions (default is sized from server RAM)
WORKER_SLOTS_OVERRIDE=4 ./local/deploy.sh linkedgrow --ssh=ALIAS --domain-type=cloudflare --domain=linkedgrow.example.com
```

## Requirements

- **RAM:** 4GB minimum (worker ~3GB with Chrome, app ~1GB, database ~512MB)
- **Disk:** ~4GB (Docker images, most of it the browser in the worker image)
- **Port:** 3000
- **Database:** libSQL, bundled. No external database and no `DB_HOST` to pass
- **Domain:** recommended. LinkedGrow answers on whatever address you open, so an SSH tunnel works for a first look

> **Dedicated server recommended.** One worker slot is one concurrent Chrome session. The installer sets `WORKER_SLOTS` from the memory it finds: 1 below 3.5GB, 2 up to 8GB, 4 up to 16GB, 8 above that.

## Stack (3 containers)

| Container | Image | RAM | Role |
|-----------|-------|-----|------|
| db | ghcr.io/tursodatabase/libsql-server:latest | ~512MB | Database, bundled |
| app | ghcr.io/digihold/linkedgrow:latest | ~1GB | Next.js dashboard and API on port 3000 |
| worker | ghcr.io/digihold/linkedgrow-worker:latest | ~3GB | Chrome under Xvfb, runs the agents and the publishing |

The worker starts only once the app answers `/api/health`, because the app generates the instance secrets on its first start and the worker reads them back from the same directory.

## After Installation

1. Open the app in a browser and create the first account. That account administers the instance, and sign ups close once the setup wizard finishes.
2. Answer the setup wizard once, which asks for the AI key that runs the agents, the spending ceilings, the proxy supplier, email and storage.
3. Connect a LinkedIn account, then create an agent and describe who you sell to.

No `.env` is written by the installer and no secret has to be generated by hand. The app writes `AUTH_SECRET` and `ENCRYPTION_KEY` into `/opt/stacks/linkedgrow/config/secrets.env` on the first start.

## Configuration

Settings live in the wizard, not in environment variables. The compose file exposes the two that a server operator may want to change:

| Variable | Default | Purpose |
| --- | --- | --- |
| `WORKER_SLOTS` | sized from RAM | Concurrent Chrome sessions the worker may open |
| `LINKEDGROW_VERSION` | `latest` | Published image tag to run |

Edit `/opt/stacks/linkedgrow/docker-compose.yaml` and run `docker compose up -d` to apply either one.

## Limitations

- **Dedicated server** because a real browser is running, not an API client
- **Slow first start** since the images are about 4GB and the app applies its migrations before it answers
- **One dedicated address per LinkedIn account** is the supported way to run this. LinkedIn treats a shared address badly, and the wizard asks for a proxy supplier for exactly that reason
- **Selector maintenance** is the standing cost of driving a real interface. LinkedIn changes its pages and the project follows

## Backup

Data in `/opt/stacks/linkedgrow/`:

- `db-data/` - the database
- `config/` - `AUTH_SECRET` and `ENCRYPTION_KEY`, generated on the first start
- `uploads/` - media attached to posts
- `profiles/` - the Chrome profile of each connected account

Back up `config/` together with `db-data/`. Without the original `ENCRYPTION_KEY` every stored LinkedIn password, 2FA secret and API key in that database stays unreadable, and there is no recovery path.
